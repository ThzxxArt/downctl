## 2. 核心问题：一次替换 = 永久、自我认证的静默损坏

### 2.1 机制（代码级）

0.1.3 的主题是"状态可信"：位图绑定 **URL 身份**（`pieces.py:75-77`），完成标记绑定
**大小 + mtime + URL 身份**（`pieces.py:294-304`）。但两处状态**都不绑定对象版本**：

| 环节 | 现状 | 位置 |
|---|---|---|
| 区间请求 | 只发 `Range`，从不发 `If-Range` | `http_transport.py:66-67` |
| 分片响应 | 只区分 `200` 与"非 200"，**不校验 `Content-Range`** | `transfer.py:106-109` |
| 位图 | 只有 `url_sha256`，无 ETag/Last-Modified | `pieces.py:62-77` |
| 完成标记 | 只有 size/mtime/identity/checksum，无版本见证 | `pieces.py:290-304` |
| 跳过判定 | 标记有效即视为"完成可证明" | `pieces.py:456`、`engine.py:195-204` |

全仓库检索 `If-Range` / `ETag` / `Last-Modified` / `Retry-After` 命中 **0**；
`Content-Range` 仅出现在 `probe.py`（用于探测大小），**传输路径从不校验**。

### 2.2 实证（可复现，脚本见附录 A）

场景：URL 不变、大小不变、服务端内容被替换（重发 release 资产、重传模型权重、
覆盖数据分片）；本地存在一份"前一半已完成"的**受信任**位图。

```
第一阶段：exit code = 0
  sha256(服务端 V2 真值) : c2a440204d135e98691643804fc9782f435eeb8382b2cc85a99e3e1b0d2e3551
  sha256(落盘结果)       : 769f02a72d463d254e56575c62758b0464588fc758be6a737b931245366f4fba
  first half is old V1 : True
  second half is new V2: True
  => SPLICED (silent corruption): True
  发出的区间请求 : 2   含 If-Range 头? : False   含 If-None-Match? : False
  写入了完成标记 : True
```

**并且损坏会盖章固化**（同一脚本第二阶段，服务端持续提供 V2）：

```
phase 1 exit=0  corrupted=True
phase 2 exit=0  still corrupted=True   unchanged=True
        HTTP 请求数 = 1（仅一次 HEAD 探测）
        stdout = 'done: 1/1 files -> .../model.bin'
phase 3 (--skip-existing) 仍损坏
phase 4 (--force)         repaired=True   ← 唯一出路
```

即：**普通重跑不会修复，`--dry-run`/`status` 也看不出来，工具每次都以退出码 0 宣称成功。**

### 2.3 这违反项目自己的公开承诺

| 文档原话（逐字核对，非转述） | 位置 | 是否成立 |
|---|---|---|
| "绝不从头重下、绝不静默损坏" | `README.md:19`；`docs/index.zh.md:9` | ✗ |
| "防静默损坏：中断残留的稀疏文件、中间有空洞的文件不会被误判为'已完成'" | `README.md:58` | ✗（本次不是稀疏/空洞，是**两个版本的字节拼接**） |
| "换了 revision、镜像源换了对象、同名不同 URL，都会自动丢弃旧账本，**绝不把两个对象的分片拼进同一个文件**" | `README.md:57` | ✗（只覆盖"不同 URL"这一个维度；**同一 URL 换内容不在内**） |
| "换了 URL（revision、镜像对象、同名不同源）会丢弃旧位图，绝不拼接两个对象的字节" | `docs/cli.zh.md:63` | ✗（同上） |
| "旧账本可能把两个 revision 的分片拼在一起"（0.1.3 明确要防的风险） | `docs/upgrading.zh.md:56` | 部分：0.1.3 只堵住了 revision/URL 维度，**未堵住同 URL 换内容** |
| "Completion is recorded in `<file>.downctl-done` … That marker is what lets a later run skip a finished size-known file without trusting its size"（此处为忠实转述，原文**没有** "proof of completion" 字样） | `docs/cli.md:55-67` | 部分成立（标记无版本见证，无法察觉源端已换版） |

**一个值得注意的细节**：`docs/upgrading.zh.md:56` 说明作者**已经意识到"拼接"这类风险**
并刻意防御——只是防御维度选在了 URL/revision，而不是对象版本。本方案的 T1/T2
正是把同一套思路补到缺失的那个维度上，而不是引入新的安全模型。

按 0.1.3 "声称必须可证明"的标准，这既是**代码缺陷**，也是**文档失真**。

## 3. 变更必要性（Change Necessity）

- **仅改文档不够**：文档改成"可能拼错"等于承认产品不可信；而"绝不静默损坏"是该项目的
  核心卖点，不能降级为免责声明。
- **仅加配置开关不够**：给用户一个 `--verify-etag` 开关，等于把默认行为继续留给损坏。
- **最小代码边界**：三处持久化格式各加一个"版本见证"字段，传输层在区间请求上附带
  `If-Range` 并校验 `Content-Range`，跳过判定改为"无见证即不称已证明"。不新增插件类别、
  不新增常驻进程、不改变热路径的分片循环结构（仍不穿越插件边界，符合 `CONTRIBUTING.md:35`）。

## 4. 波及面三角（Ripple Signal Triage）

本次触发信号：**schema / 持久化 / 契约 / 迁移 / 退役**。

| 面 | 现有唯一属主 | 本次影响 | 下游消费者 |
|---|---|---|---|
| 位图 `.downctl-pieces` | `core/pieces.py` | **不升版本**（v4 追加 `validator` 字段） | `engine._completed_bytes/_remaining_bytes`、`app.collect_status/find_cleanables`、`status` 命令 |
| 完成标记 `.downctl-done` | `core/pieces.py` | v2 → **v3**（新增 `validator`/`witness`） | `engine._proven_complete`、`pieces.resolve`、`clean` |
| 失败清单 `.downctl.failed` | `app.py`（`_fmt_url`/`_parse_failed_line`） | v3 → **v4**（追加 validator） | `--retry-failed`、`status`、`clean` |
| 传输契约 `Transport.request` | `plugin/protocols.py` | **不变**（`headers` 已可传 `If-Range`，`Response.headers` 已暴露 ETag） | 第三方 transport 插件 |
| 探测 API `probe.probe_size` | `probe.py` | **不变**（新增 `probe_metadata()`，旧函数保留为包装） | HF/GitHub/S3 源插件 |

**关键结论：本方案不需要提升 `API_VERSION`。** 插件契约（`protocols.py`）无需变更，
第三方插件不会因 0.1.4 被拒绝。这是把风险控制在"单进程状态格式"内的核心依据。

**新增属主检查**：不新增属主。`validator` 归一化逻辑归属 `urls.py`（它已经是"身份与脱敏"
的唯一属主），不新建模块。

## 5. 兼容性与迁移边界

| 对象 | 旧格式 | 新格式 | 迁移策略 | 用户可见代价 |
|---|---|---|---|---|
| 位图 | v4（有 URL 身份、无版本见证） | **仍是 v4**，追加 `validator` 字段 | 见证比对决定去留：服务器报了版本而账本没记 → 重置；服务器不报版本 → 与 0.1.3 一样续传 | 只有"服务器报版本"的未完成下载会重来一次；**降级回 0.1.3 不会截断任何文件** |
| 完成标记 | v2 | **仍是 v2**，追加 `validator` 字段 | **继续信任** 0.1.3 标记（它是"完成记录"而非"续传账本"，最多导致**陈旧跳过**，不会拼接）；运行真正把目标跑完（或跳过被校验和证明）时补写见证 | 无强制重下（刻意避免重演 0.1.3 在 WSL/Windows 上的"全量重下一次"） |
| 失败清单 | v3 | **保持 v3** | 继续读 v3；重试路径总是重新探测，不存陈旧见证 | 无 |
| 配置键 | — | 新增 `[core] require_witness` | 未知键仍被忽略 | 无 |

**迁移不变量**：升级本身不删除任何用户数据文件（沿用 `docs/upgrading.md` 承诺）；
新的"不可证明"判定只影响**续传账本**，不影响已下载文件。

## 7. 版本主题与目标

> **0.1.4 —— "内容可信"**
> 0.1.3 让账本知道"这份状态属于**哪个 URL**"；0.1.4 必须让账本知道
> "它属于**哪个版本的对象**"，并且在**没有见证**时拒绝宣称"已完成"。

**可判定的版本目标（全部为可执行断言）**

1. 同一 URL 上内容被替换（大小相同、ETag 变化）时，续传**不得**产出拼接文件：
   要么重新完整下载，要么明确报错；退出码与消息必须反映事实。
2. `Content-Range` 与请求区间不符的 206 响应必须被拒绝，不得写入错误偏移。
3. 完成标记只在校验过对象版本（或显式校验和）时才宣称"已证明完成"。
4. 存在 `downctl verify` 这一条不依赖 `--force` 的修复/复核通道。
5. 上述 1–4 全部有回归测试，且集成测试服务器具备 ETag / If-Range / 416 / 错区间夹具。

## 8. 任务分解

> 每项含：目的 / 最小改动边界 / 兼容性 / 验收 / 风险与工时。
> 工时以"一人全职"计。

### P0 —— 阻断级（正确性，必须先做）

**T1 状态格式加入版本见证**
- 目的：让持久化状态能判断"远端对象是否还是同一个版本"。
- 改动：`core/pieces.py`（`BITMAP_VERSION 4→5`、`COMPLETION_VERSION 2→3`；
  `Bitmap` 增加 `validator: str`；`bitmap_trusted()` 增加 validator 比对；
  `save_completion()`/`completion_valid()` 记录并比对 `validator`、`witness`）；
  `urls.py` 新增 `normalize_validator(headers)`（ETag 优先、`Last-Modified` 兜底、
  弱 ETag `W/` 前缀归一、缺失返回 `""`）。
- 兼容：v4 位图不受信（§5）；v2 标记继续受信并可就地升级。
- 验收：`pytest tests/unit/test_state_trust.py -q` 全绿；新增用例
  "validator 变化 ⇒ `completion_valid` 为假、`bitmap_trusted` 为假"。
- 风险：中（格式变更）；工时：1.5 天。

**T2 条件区间请求与响应校验**
- 目的：从协议层堵住拼接。
- 改动：`builtin/transports/http_transport.py`（区间请求附带 `If-Range: <validator>`）；
  `core/transfer.py` `_PieceFetcher.run()`（解析 `Content-Range`，断言
  `start/end/total` 与请求一致，否则 `raise TransportError`；把"因 If-Range 失配返回 200"
  与"服务器不支持 Range 返回 200"区分开，前者必须**重置账本**而非降级单流）。
- 兼容：`Transport` 协议不变（仅多传一个 header、多读一个 header）。
- 验收：复现脚本第一阶段结果由 `SPLICED=True` 变为 `SPLICED=False` 且文件等于服务端真值；
  新增集成夹具"ETag 变化 + If-Range 失配 ⇒ 200"与"206 返回错误区间"。
- 风险：高（触及核心热路径）；工时：2 天。

**T3 区间不可满足的恢复路径**
- 目的：`416`（以及条件请求下的 `412`）现在是 `PermanentHTTPError` 硬失败，无自救。
- 改动：`http_transport.py` 对 416 抛出可识别异常或返回状态；`core/engine.py`
  捕获后**重置该目标账本并重下一次**（仅一次，避免死循环）。
- 验收：夹具返回 416 ⇒ 最终下载成功且只重置一次。
- 风险：低；工时：0.5 天。

**T4 内容不变式回归测试（本版最重要的测试）**
- 目的：现有测试断言的是"位/标志/退出码"，**没有一条断言"最终字节等于被获取版本的真值"**
  —— 这正是本缺陷能穿过 4 个版本的原因。
- 改动：`tests/integration/conftest.py` 增加 ETag/Last-Modified/If-Range/416/错区间夹具；
  新增 `tests/integration/test_content_truth.py`：参数化
  "中断点 × 服务端是否换版 × 是否有校验和"，断言最终 `sha256(文件) == sha256(服务端当前真值)`，
  或在无见证时断言**明确失败**而非静默成功。
- 验收：`pytest tests/integration/test_content_truth.py -q` 全绿；故意回退 T1/T2 时该套测试必须失败。
  同时补三处审计认定的硬缺口：
  ① **真实子进程重启续传**（全仓库第一个 `subprocess` 用例：进程 A 下载中断 → 进程 B 重跑 →
  只补缺失分片；含 `SIGTERM` ⇒ 退出码 130 与进度落盘）；
  ② 修正 `tests/integration/test_transfer.py:138-166`——它名为"stall 后续传"，实际第二次调用
  **换了 URL**（`/stall` → `/file`），identity 不匹配触发账本重置，是整文件重下；改为同 URL
  续传并断言只抓缺失区间；
  ③ 给错误分类体系补上第一个引用（`TransportError`/`TransientHTTPError`/`PermanentHTTPError`
  当前在全部测试中**零引用**，与 T10a 的缺陷互为因果）；
  ④ 修正 `tests/integration/test_engine.py:162-178`（`min_split_size` 只断言路径后缀，
  未断言单连接）为断言只发出 1 条区间请求。
- 风险：低；工时：2.5 天（含子进程与信号用例）。

### P1 —— 可证明与可修复（让"完成"可复核）

**T5 `downctl verify` 与 `--recheck`**
- 目的：给出一条不依赖 `--force` 的复核/修复通道（当前唯一出路是整文件重下）。
- 改动：新增 `app.cmd_verify` + `cli.add_verify_parser`（`downctl verify [DIR] [--json]
  [--checksums FILE] [--repair]`）：对每个带标记/边车的文件复算摘要，报告
  `ok / mismatch / unverifiable`；`--repair` 时删除被证伪的标记与数据（**破坏性动作需显式开启**）。
- 验收：`downctl verify` 能识别 §2.2 造出的损坏文件并返回退出码 1；`--json` 输出与
  `status --json` 风格一致。
- 风险：低；工时：1.5 天。

**T6 "无见证不称已证明"策略落地**
- 目的：让跳过判定与真实证据对齐。
- 改动：`engine._proven_complete` 与 `pieces.completion_valid` 引入三态
  `witness: "validator" | "checksum" | "none"`；服务端不提供任何验证器时，
  普通重跑仍可跳过（陈旧但自洽），但 `--skip-existing` 与 `verify` 报告须标注
  `unversioned`；新增 `[core] require_witness`（默认 `false`，见决策 D2）。
- 验收：对"无 ETag 服务端"的用例，`--skip-existing` 输出标注 `unversioned`，
  JSON 记录含 `"witness": "none"`。
- 风险：中（语义变化需同步 5 处文档）；工时：1 天。

**T7 文档真值修正（中英双语）**
- 目的：消除 §2.3 的失真声称。
- 改动：`README.md`、`README.en.md`、`docs/{cli,design,sources,troubleshooting,upgrading}.md`
  及其 `*.zh.md`：把"绝不静默损坏"限定为"在可判定条件下"，补一节

### P2 —— 规模与网络礼貌

**T8 解析/探测并发化**
- 目的：当前 `app.py:862-891` 与 `541-560` 是**串行** `await`，N 个目标 = N×RTT 才开始下第一个字节
  （`hf://` 整仓 50 文件即 50 次串行 HEAD）。
- **实测**（脚本见附录 C）：24 个目标、每次 HEAD 0.2s、已显式传 `-j 8` ⇒ 墙钟 **6.09s**，
  HEAD 请求 24 次。按用户已给出的并发度应为 0.60s，**慢 10.1 倍**；探测阶段完全无视 `-j`。
- 改动：`app._resolve_targets`/`_get` 用有界 `asyncio.Semaphore`（复用 `--jobs`，
  上限可配 `[core] probe_jobs`，默认 8）并发解析与探测，保持"失败即记录"语义不变。
- 验收：50 目标本地服务器场景下，首个字节时间从 O(N) 降为 O(N/8)；错误聚合顺序与
  当前 `failures` 列表一致（顺序敏感，需测试固定）。

**T9 批量磁盘预算**
- 目的：`engine.py:325-334` 只对**单个文件**做预检，`-j 4` × 4 个 50 GB 文件可在 100 GB 磁盘上
  全部通过，然后在写入过程中 ENOSPC。
- 改动：`core/disk.py` 增加批量预算（总需求 + 预留），`download_all` 入口预检一次并按

- 风险：低；工时：1 天。

**T10 失败分类与重试语义收紧（两个独立缺陷）**

- **T10a 探测阶段的瞬时错误被当成永久失败。**
  实测（脚本见附录 C）：HEAD 返回 `500` ⇒ 进程 **1.30s 内退出码 1**，仅 2 次请求，
  完全没有重试，并被记入 `.downctl.failed`。原因：`probe.probe_size()` 原样返回 5xx
  （`probe.py:46-47`），而 `app._get` 对 `status >= 400` 一律立即抛错（`app.py:866-871`），
  引擎的重试循环根本没机会运行。这与 CHANGELOG 0.1.1 的声称
  "probe treats any HTTP >= 400 as a failure (4xx permanent, **5xx/other via the
  transport's transient classification**)" 直接矛盾——`probe.py` 走的是裸 `session.head`，
  从未经过传输层分类。
  改动：让 5xx/429/408/425 在探测阶段可重试（复用 `TransportError` 语义），
  4xx 保持永久；失败日志与 JSON 记录需区分 `transient-exhausted` 与 `permanent`。
  验收：夹具 HEAD 500 若干次后转 200 ⇒ 最终下载成功；HEAD 404 ⇒ 立即失败且不重试。

- **T10b 引擎阶段默认无限重试且不遵守 `Retry-After`。**
  实测：HEAD 200、区间 GET 永远 500 ⇒ **20 秒内 43 次请求、进程仍在运行、无任何截止机制**
  （`retries=0` 默认无限：`config.py:62` + `engine.py:414`；退避上限 60s；
  `Retry-After` 在 `src/` 中出现 **0** 次）。一个永久 5xx 的目标会让批处理与 CI 无限挂起。
  改动：解析并遵守 `Retry-After`（429/503）；新增 `--max-time SECONDS`（单文件墙钟上限，
  默认不限）；默认值是否收紧见决策 D3。
  验收：夹具返回 `429 + Retry-After: 2` ⇒ 实际等待 ≥2s；`--max-time 5` 下目标 5s 内放弃并记入失败清单。
- 风险：低；工时：1.5 天（含 T10a）。

### 15.2 与本文的偏差（三处，均为"按证据修正方案"）

| # | 方案原文 | 实际做法 | 理由 |
|---|---|---|---|
| 1 | §4 波及面表：失败清单 `.downctl.failed` v3 → v4（追加 validator） | **保持 v3，不追加** | 重试路径（`--retry-failed`）总是重新探测目标，`validator` 只能来自当次探测；把上次的见证写进失败清单，唯一可能的用途是"用陈旧见证做续传判定"——那正是本版要消灭的东西。存而不用属于"已定义但不用"的第三种状态，反熵原则要求不引入 |
| 2 | §8-T9：`-j` 自动收敛到可行值 | **不做并发收敛**；总量不可行时整批拒绝 | 已写入磁盘的字节始终占盘，并发度不改变"这批能不能装下"这一事实；收敛旋钮在数学上是死代码（总量可行 ⇒ 全员可行）。保留的部分才是真实约束：按设备分组的总量预检 + 一次性给出总需求与可用空间 |
| 3 | §8-T10a：探测阶段"复用 TransportError 语义"重试 | 重试次数固定有界（`PROBE_ATTEMPT_LIMIT = 3`），退避封顶 5s，且 `Retry-After` 优先 | 探测没有可保留的进度，一次批处理里每个死目标若都按下载的指数退避（5/10/20/40/60s）重试，整批会被拖到分钟级。实施中途实测发现该退避会让测试套件挂起 10 分钟——**以实测修正方案** |
| 4 | §4/§5：位图 v4 → v5、完成标记 v2 → v3 | **两个版本号都不动**，各自追加 `validator` 字段 | 独立对抗式审查复现：0.1.3 的 `load_completion` 对 `version > 2` 直接返回 `None`，于是它把 0.1.4 写出的*已完成*标记当成"无证明状态"，`resolve()` 随即 `discard()` **截断整个已完成文件**。升版本号 = 把"降级"变成数据丢失；追加字段则被老读取器忽略（已用 `v0.1.3` tag 的代码逐行核对），降级安全。保护强度不变：拒绝旧账本的依据是"见证比对"，不是版本号 |

另有两处方案未预见、实施中必须补的**新增防线**（已写入代码与文档）：

- **见证抖动降级**（风险登记 §13 的中风险项）：服务器每次响应都换 ETag 时，`If-Range`
  永不匹配 → 方案原逻辑会"重启一次后放弃"，等于让这类服务器的多连接下载永久失败。
  实测确认后补：`ContentChangedError.validator == 发送的见证`（服务器拒绝自己的见证）
  或二次探测又变（抖动）→ **丢弃见证继续下载**（标注 unversioned），而不是失败。
- **标记宽松规则 vs 账本严格规则**：账本（续传）用严格比对（防止拼接），完成标记用
  "两侧都有见证才比对"（防止服务器停止/开始发 ETag 就引发全量重下）。两者由不同谓词
  承担（`witness_matches` / `completion_valid`），语义差异已在 docstring 与文档中写明。
- **`--recheck` 的语义由引擎拥有**：CLI 只写 `task.meta["recheck"]`，由 `engine`
  推导"同时要求见证"并决定是否复用标记里记录的摘要重新哈希。这样直接调用引擎的第三方
  代码不会获得比 CLI 更弱的保证（单一属主，而不是两处各写一份判断）。

- `/tmp/downctl_splice_demo.py` —— 证明"同 URL 换内容 ⇒ 拼接 ⇒ 退出码 0 ⇒ 写入完成标记"。
- `/tmp/downctl_sticky_demo.py` —— 证明"拼接结果被永久盖章，普通重跑与 `--skip-existing`
  都不修复，仅 `--force` 可修复"。
- `/tmp/downctl_serial_probe.py` —— 量化串行探测：24 目标 × 0.2s HEAD，`-j 8` 下仍耗 6.09s
  （理想 0.60s，**慢 10.1 倍**）。
- `/tmp/downctl_unbounded_retry.py` —— 量化失败分类：探测阶段 HEAD 500 ⇒ 1.30s 退出码 1
  （永不重试）；引擎阶段 GET 500 ⇒ 20s 内 43 次请求仍在继续（无截止机制）。

四者均自建本地 HTTP 服务器（支持 Range 与 ETag），自行构造受信任位图，
通过子进程调用 `python -m downctl`，并以 `sha256` 对比服务端真值。
运行时无需网络与外部凭据。
