## 2. 通读结论：边界在哪里被打破

### 2.1 做对了、0.1.6 不许动的

1. **协议是结构化的，不强迫继承**（`protocols.py:1-11`）。第三方插件不必 import downctl。
2. **内置插件走同一条注册路径**（`builtin/__init__.py:42`），可以被同名插件覆盖。
3. **引擎只认 `DownloadTask`**（`core/task.py`），不回头看用户输入。
4. **请求只有一个收口**（`policy_request`），代理与凭据的逐跳决定都在那里。
5. **失败有分类**（`permanent` / `transient-exhausted` / `timeout`），机器可判重试。
6. **状态写入有原子性与"拒绝即不动"**（0.1.5 的三层守卫）。

### 2.2 按生命周期看，缺的是三段时间

| 阶段 | 现状 | 缺口 | 0.1.6 |
|---|---|---|---|
| **下什么** | `get` 接受多个 target 字符串；`-l` 读一个纯文本清单 | 没有"一组目标 + 每组自己的选项"的模型；`-l` 不能表达 `include`/`checksum`/`dir` | **F1 `batch` + `JobSource`** |
| **凭什么** | 每个 source 自己读 `[plugins.x] token` 与环境变量（`plugin/credentials.py` 只覆盖 config/env 两个来源） | 没有"凭据从哪来"的插件；`netrc`/helper/SSO 无处安放；无法按主机配置 | **F2 `auth` + `AuthProvider`** |
| 怎么传 | `transport` 插件 ✅ | — | — |
| 怎么验 | `verifier` 插件 ✅ | `pgp` 签名类验证没有契约（stretch） | 暂不做 |
| 怎么报 | `reporter` 单通道 | 指标只能靠 hook 自己拼；无 Prometheus 形状 | `metrics` hook |
| 下完做什么 | `hook` 只观察 | 没有"通知"语义的内置实现 | `notify` hook |
| **怎么交付** | 无 | 下完的文件无法以"同样的 Range/ETag 语义"交给别的机器 | **F3 `serve` + `Server`** |

### 2.3 内核的六个"没做到"

| # | 事实 | 证据 | 后果 |
|---|---|---|---|
| B-1 | `select_source` 直接调用每个插件的 `can_handle`，没有异常隔离 | `registry.py:81` | **一个第三方 source 在 `can_handle` 里抛异常，会让每一次运行都崩**，而它只是"被问了一句" |
| B-2 | 入口点只接受类或实例：`factory() if isinstance(factory, type) else factory` | `loader.py:67-68` | `def make(): return MySource()` 这种最常见的工厂写法会被当成插件本身注册，然后校验失败 |
| B-3 | 同名注册静默覆盖 | `registry.py:68` | 两个已安装包重名时，后加载的赢，没有任何提示；`plugin list` 也看不出谁赢了 |
| B-4 | **每个内置插件被注册两次**：`builtin.register_all` 一次，同名的 entry point 再一次（后者覆盖前者） | 复现：`metadata.entry_points(group="downctl.sources")` 返回 6 个内置；`pyproject.toml:87-120` 与 `builtin/__init__.py:32` 各声明一遍 | 每次运行多实例化 22 个对象；entry point 路径写错时被代码注册掩盖；`origin` 永远显示 entry point，无法回答"这个插件从哪来" |
| B-5 | 能力靠 `getattr` 试探，没有声明 | `protocols.py:81-88`、`engine.py` 多处 | 新能力（如"这个 source 认 `--include`"）只能靠约定，调用方无法在运行前知道 |
| B-6 | 没有插件作者的自检工具 | 无 `plugin check` / `plugin new` / `downctl.plugin.testing` | 第三方只能靠读文档 + 跑一遍才知道自己写对了没有 |

## 3. 主题与设计原则

**0.1.6 主题：把还没被插件化的三段生命周期，变成和另外六类一样的插件。**

四条原则，按优先级：

1. **一个阶段只有一个协议。** 新增 `JobSource` / `AuthProvider` / `Server` 三类，各自只回答一个问题。
2. **内置插件与第三方同接口。** 三类新协议的内置实现走同一条注册路径，可被同名覆盖。
3. **API v1 不破。** 只做加性变更：新类别、新可选方法、新配置节。旧插件照常工作。
4. **一个决定只在一个地方做。** 作业选项的合并、凭据的归属、服务端的 Range 语义，各自只有一个属主。

## 4. F1：批量作业（`downctl batch` + `JobSource`）

### 4.1 问题

`get` 已经能一次接多个 target，但**它们共享同一组选项**。真实场景是一组目标
各有各的目录、glob、校验和与钩子：

```bash
downctl get hf://org/a@main hf://org/b@v2 https://x/tool.tar.gz \
  -d models --include '*.safetensors' --hook archive
```

上面这条命令里，`--include` 会作用于 `tool.tar.gz`（无匹配则报错），`--hook archive`
会试图解压 `.safetensors`。用户只能拆成三条命令，于是失去统一的失败清单与退出码。

`-l/--list` 只是"每行一个 target"，无法表达任何 per-target 选项。

### 4.2 数据模型

新增 `src/downctl/core/job.py`：

```python
@dataclass(frozen=True)
class Job:
    name: str                      # 稳定标识，用于 --job 过滤与事件
    targets: list[str]             # 该作业的目标（可多个，共享选项）
    options: dict[str, object]     # get 选项的子集（见 4.3）
    origin: str = ""               # 作业文件路径，用于报错定位
```

`Job` 属于 **core**，不属于某个插件：它是引擎的输入形状，正如 `DownloadTask`。

### 4.3 选项子集

作业可以覆盖 `get` 的**运行期**选项，但**不能**覆盖会改变批次语义的选项：

| 允许 | 不允许（在作业里报错） |
|---|---|
| `dir` `jobs` `connections` `stall` `checkpoint` `max_time` `probe_jobs` `piece_size` `min_split_size` `limit_rate` `retries` | `list`（批次自己就是清单） |
| `force` `skip_existing` `require_witness` `recheck` `dry_run` `continue` | `retry_failed`（批次不走失败清单重放） |
| `checksum` `checksums` `include` `exclude` `revision` `source` `proxy` `mirror` | `local_plugins`（进程级，只能顶层给） |
| `hook` `header` `user` `user_agent` `output`（仅当该作业只有一个 target） | `reporter`（一次运行一个报告器） |

未知键 → **在运行任何作业之前**报错，并列出允许的键。这条规则是 0.1.5
"配置错误必须说清楚"的延续。

### 4.4 协议

新增到 `plugin/protocols.py`：

```python
@runtime_checkable
class JobSource(Plugin, Protocol):
    """把一份作业文件读成 Job 列表。"""

    formats: tuple[str, ...]        # e.g. ("toml", "tml")

    def can_handle(self, path: str) -> bool: ...
    async def load(self, path: str, ctx: RuntimeContext) -> list[Job]: ...
```

注册类别 `jobsource`，入口点组 `downctl.jobsources`。
`Registry.CATEGORIES` 增加一项；`CATEGORY_METHODS` 增加 `("can_handle", "load")`。

**为什么不是把作业文件做成一个 `Source`：** `Source.resolve` 只能返回
`DownloadTask`，而 `dir`/`include`/`force` 是**运行级**参数，无法塞进一个 task 而不
污染引擎的契约。`Job` 是"运行计划"而不是"一个文件"，它需要自己的形状。

### 4.5 文件格式（内置 `toml`）

```toml
version = 1

[[job]]
name = "llama-3-8b"
targets = ["hf://meta-llama/Llama-3-8B@main"]
dir = "models/llama"
include = ["*.safetensors", "*.json"]
checksum_manifest = "checksums.txt"   # 可选：按 basename 匹配

[[job]]
name = "tool"
targets = ["https://example.com/tool.tar.gz"]
checksum = "sha256:9f2c..."
hooks = ["archive"]
```

- `version` 必填且必须为 `1`；未来版本 → 明确报错（"written by a newer downctl"）。
- `[[job]]` 至少一项；`name` 缺省为 `job-<序号>`，重复 name → 报错。
- `targets` 字符串或字符串数组均可。
- 选项名与 `get` 的长选项一一对应（下划线形式），未知键报错。

`json` 内置读同一形状的 JSON（`{"version":1,"jobs":[...]}`），用于程序生成。

### 4.6 CLI

```
downctl batch <file> [--job NAME]... [--dry-run] [--continue]
                     [--job-source NAME] [--json? 由 --reporter 决定]
```

- 作业按文件顺序**串行**执行（并发留给作业内部的 `jobs`/`connections`）。
  理由：作业之间可能写同一个目录；0.1.6 先保证可预测，并行留到有证据需要时。
- 所有作业**先解析、先校验**，再开始第一个下载（fail-fast）。
- 整次运行共享一个 `Registry` 与一个 reporter；每个作业新建自己的 `Session` 与
  `EventBus`，因为作业的 `header`/`user`/`auth` 与钩子不能泄漏到下一个作业。
- 失败清单按**目标目录**：每个作业写 `<job dir>/.downctl.failed`；共用同一目录的作业
  合并进同一份清单，重放用 `get --retry-failed -d <该目录>`。
- 每个作业发 `on_start` / `on_finish`，payload 增加 `"job": name`；`on_task_*`
  的 payload 沿用 task，task 的 `meta["job"]` 也写入作业名（JSON 报告器把它带出去）。
- 摘要：每个作业一行（`ok/failed/bytes/elapsed`），最后一行总计。
- 退出码：`0` 全部成功；`1` 至少一个目标失败；`2` 作业文件非法（解析/校验失败，
  一个字节都没下）。

### 4.7 实现路径（不重写 `_get`）

`_get` 现在把"解析 → 探测 → 去重 → 下载 → 失败清单 → 摘要"写在一个 275 行的函数里，
且入参是 `argparse.Namespace`。0.1.6 只做一次**提取**，不改变行为：

1. 把 `_get` 的主体提取为 `async def _run_plan(plan: RunPlan, env: RunEnv) -> RunResult`：
   - `RunPlan`：`targets`、`options`（已合并的配置）、`checksums` 等；
   - `RunEnv`：`registry`、`session`、`events`、`reporter`、`cfg`。
2. `cmd_get` = `_build_plan(args)` → `_run_plan(...)` → 打印摘要。
3. `cmd_batch` = 读作业 → 每个作业 `_build_plan(namespace)` → `_run_plan(...)`
   （共享 `RunEnv`）→ 批量摘要。
4. `_default_get_args()`（`app.py:2339`）已经是现成的 Namespace 模板，作业选项
   直接覆盖它。

**风险控制：** 提取的第一步是**纯搬运**，先让 `895 passed` 保持不变，再加
`batch`；两件事不许在同一个提交里做。

## 5. F2：身份提供者（`AuthProvider`）

### 5.1 问题

今天凭据有三个来源，各写各的：

| 目标 | 现在怎么拿凭据 | 问题 |
|---|---|---|
| HuggingFace | `[plugins.huggingface] token` → `HF_TOKEN` | 只认这两个来源 |
| GitHub | `[plugins.github] token` → `GITHUB_TOKEN` | 同上 |
| S3 | `[plugins.s3] access_key` → `AWS_*` | 不认 `~/.aws/credentials`、不认 `credential_process` |
| 普通 HTTP | `-u user:pass` 或 `-H Authorization:…` | 无 `~/.netrc`、无 helper、无按主机配置 |

企业里最常见的三种做法——`~/.netrc`、`gh auth token` 之类的 helper、
按主机配置——一个都没有。而"凭据该发给谁"的规则（0.1.5 建立的按源绑定）
已经在了，缺的是**凭据从哪来**这一层。

### 5.2 数据模型

`src/downctl/core/credentials.py`（新文件，与现有 `plugin/credentials.py`
的"配置/环境解析"并存，后者保留为兼容层）：

```python
@dataclass(frozen=True)
class AuthMaterial:
    headers: Mapping[str, str] = field(default_factory=dict)
    basic: tuple[str, str] | None = None
```

### 5.3 协议

```python
@runtime_checkable
class AuthProvider(Plugin, Protocol):
    """为一台主机提供凭据。"""

    def can_handle(self, host: str) -> bool: ...
    async def material(
        self, host: str, ctx: RuntimeContext, options: Mapping[str, object]
    ) -> AuthMaterial | None: ...
```

注册类别 `auth`，入口点组 `downctl.auths`。

**只返回"材料"，不返回"决定"。** 发给谁、是否跨重定向，仍由
`policy_request` 的源绑定规则决定——这是 0.1.5 已经做对的部分，不许出现第二个属主。

### 5.4 配置

新增 `[auth.<host>]` 节（不是 `[plugins.*]`：它描述的是"主机"，不是某个插件实例）：

```toml
[auth."huggingface.co"]
provider = "env"
env = "HF_TOKEN"
header = "Authorization"
prefix = "Bearer "

[auth."private.example.com"]
provider = "command"
command = "pass show example/token"
ttl = 300                     # 秒；0（默认）= 整个运行复用

[auth."*.corp.example"]
provider = "netrc"
```

匹配顺序：**精确主机 → 后缀匹配（`*.corp.example`）→ 无**；最长后缀胜。
同一主机只允许一个 provider（重复定义报错）。解析结果按 `(origin, rule,
provider)` 缓存：`ttl = 0`（默认）表示整次运行只解析一次；`ttl > 0` 到期后重新取。

### 5.5 接线（唯一收口）

- `RuntimeContext` 增加 `auth: AuthResolver | None`。
- `AuthResolver` 以 `session` 属性（`AUTH_RESOLVER_ATTR`）挂到共享 session，与
  `ORIGIN_HEADERS_ATTR` 同一模式——`policy_request` 只需要 session 就能查到它，
  不必给 6 个调用点都加参数。
- `policy_request` 在第一跳解析一次 `material_for(url)`，**只在该跳仍属原源时附加**；
  跨源重定向一律丢弃（与现有 `Authorization`/`Cookie` 规则一致）。
- 优先级由 `_hop_headers` 的**逐头名合并**决定：`DownloadTask.headers` 先放
  （`_run_plan` 把 CLI `-H` 覆盖进同名 task 头），随后是 session 上按源绑定的 `-u`
  认证，最后是 provider 材料；后两者都只补缺失的头名，不覆盖已有值。因此显式
  `-H Authorization` 压过 provider，provider 的 `Authorization` 只在没有任何同名
  请求头时附加；provider 也可以提供其他头名，但同样只补缺。三者都只发给第一跳源。
- 缓存：按 `(origin, rule, provider)` 缓存；`ttl = 0` 整次运行复用，`ttl > 0` 到期后
  重新取（`command` provider 常见）。
- 失败：provider 失败 → 该目标 `permanent`，错误信息点名 provider 与来源
  （`command exited 1` / `env HF_TOKEN is unset`），**绝不打印值**。

### 5.6 内置

| 名字 | 选项 | 行为 |
|---|---|---|
| `env` | `env`（名或名列表）、`header`、`prefix` | 按顺序取第一个非空环境变量 |
| `command` | `command`、`timeout`（默认 10）、`header`、`prefix`、`ttl` | 运行命令，取 stdout 第一行；非零退出 → 报错；stderr 只记长度 |
| `netrc` | `path`（默认 `~/.netrc`） | 用 `netrc.netrc` 按 machine 匹配，返回 basic；POSIX 下组/世界可读时警告 |

### 5.7 诊断

```
downctl auth check https://private.example.com/x
  host      private.example.com
  rule      [auth."private.example.com"]
  provider  command (command)
  material  Authorization (len 32, from command)
```
只打印**头名与来源**，不打印值。`doctor` 增加一行：配置了哪些 host 规则、
每条规则匹配到哪个 provider。

### 5.8 安全规则（必须写成测试）

1. 跨源重定向不携带 provider 材料（复用 0.1.5 的逐跳测试形状）。
2. `auth check` 与 `-v` 输出中不出现凭据值（用一个标记值做断言）。
3. provider 抛出的异常文本进入日志前经过 `redact_text`。
4. provider 材料不写入 `DownloadTask.meta`、失败清单、JSON。
5. `command` provider 的 stdout 去掉首尾空白，只取第一行（多行视为格式错误并报错）。

## 6. F3：交付服务（`downctl serve`）

### 6.1 动机

下载器修好了"取回"，但没有"交出去"。三个真实场景：

1. **WSL / 容器**：Windows 侧下好了 30 GB 模型，WSL 里要读，走 `/mnt/` 慢且语义不同。
2. **气隙环境**：一台机器下好，局域网内其他机器要从它取，且要支持断点续传。
3. **自测**：downctl 自己的 Range/If-Range/416 逻辑，最好的对手是一个**你知道它怎么实现**的服务器。

### 6.2 协议

```python
@runtime_checkable
class Server(Plugin, Protocol):
    """把一个本地目录/文件以可续传的方式提供出去。"""

    async def serve(self, root: str, ctx: RuntimeContext, options: Mapping[str, object]) -> None: ...
```

注册类别 `server`，入口点组 `downctl.servers`。`serve` 预期长期运行，直到
`SIGINT`/`SIGTERM`；协议不规定传输层（HTTP 只是内置实现）。

### 6.3 CLI

```
downctl serve <dir|file> [--bind 127.0.0.1] [--port 8080]
                          [--auth USER:PASS] [--index] [--quiet]
```

- 默认绑定 `127.0.0.1`；绑定非回环地址时打印一行醒目警告（"this exposes the directory to the network"）。
- `--auth` 用 Basic，`secrets.compare_digest` 比较。
- `--index` 打开目录列表；默认目录请求 404。

### 6.4 HTTP 语义（内置 `http` server）

| 能力 | 规则 |
|---|---|
| `GET` / `HEAD` | 文件；`HEAD` 返回同样的头，无 body |
| `Range: bytes=a-b` / `bytes=a-` / `bytes=-n` | 单区间；`206` + `Content-Range: bytes a-b/size` |
| 多区间 | 忽略 Range，返回 `200` 全量（RFC 允许） |
| 越界 | `416` + `Content-Range: bytes */size` |
| `If-Range` | 与当前 ETag/Last-Modified 相同 → `206`，不同 → `200` 全量 |
| `ETag` | 优先取 `.downctl-done` 里记录的 witness；否则 `W/"<size>-<mtime_ns>"` |
| `Last-Modified` | 文件 mtime（HTTP-date） |
| 目录 | `--index` 时 HTML 列表（名字转义），否则 `404` |

### 6.5 安全

1. 路径解析后必须仍在 root 之下（`resolve()` + `commonpath`）；符号链接指向外部 → `403`。
2. 不跟随 `..`；URL 解码在检查之前完成。
3. 默认只绑回环。
4. 认证失败返回 `401` + `WWW-Authenticate`，不泄露路径是否存在。
5. 请求日志去掉 query（`--auth` 不进 URL）。

### 6.6 为什么它仍然是"下载器"的一部分

- 它让 downctl 的**输出**可以被 downctl 的**输入**消费（`downctl get http://127.0.0.1:8080/x`），
  这是"一切皆插件"的闭环：同一个 Range 语义，两端都实现，且两端都可替换。
- 它复用现有的状态与证据模型：`.downctl-done` 的 witness 直接成为 ETag，下载端看到的
  就是当初验证过的那一个。
- 它不引入新依赖：`aiohttp.web` 已随 `aiohttp` 提供。

### 8.1 `http_index`（source）

- 只处理**以 `/` 结尾**的 http(s) URL（优先级 5，高于 `url` 的 0），
  因此 `https://host/dir/` 自动走它，`https://host/file.bin` 仍走 `url`。
- `Content-Type: application/json` → 接受 `{"files":[{"name","size"?, "url"?}]}` 或字符串数组；
  HTML → `html.parser` 解析 `<a href>`，只接受同源相对链接，跳过 `..`、`/`、`?`、`#`。
- 应用 `--include/--exclude`；目录名（以 `/` 结尾的链接）跳过。
- 任务带 `size`（JSON 有则用，HTML 用 `Content-Length` 探测）。
- 验收：两种 fixture（Apache 风格 HTML、JSON 清单）各一个端到端测试。

### 8.2 `metrics`（hook）

- `on_finish` 时把 Prometheus textfile 写到 `path`（默认 `downctl.prom`），原子替换：
  ```
  downctl_run_duration_seconds 12.34
  downctl_files_total{outcome="ok"} 7
  downctl_files_total{outcome="failed"} 1
  downctl_bytes_total 123456
  downctl_failures_total{reason="permanent"} 1
  downctl_hook_failures_total 0
  ```
- 依赖 `on_finish` 新增的 `bytes`/`elapsed`；写失败计入 `HookTasks.record()`，
  `strict_hooks` 可见。

### 8.3 `notify`（hook）

- 两种后端，二选一：
  - `url`：POST JSON 到 ntfy 兼容端点（`title`/`priority`/`body`）；
  - `command`：用户给的命令，事件信息走环境变量（与 `exec` 同一套 `DOWNCTL_*`）。
- 默认 `events = ["on_finish"]`；`only_failures = false`。
- 后台线程发送，`HookTasks` 计数；失败 `always=True` 告警。
