# 安全公告：拼接文件（0.1.0 – 0.1.3）

**影响版本：** downctl 0.1.0 – 0.1.3
**修复：** 0.1.4 起不再产生；0.1.5 补齐下述检测路径的说明
**严重度：** 高 —— 静默数据损坏，没有任何报错
**CVE：** 未申请；这是 pre-1.0 工具，修复随常规版本发布

## 发生了什么

downctl 把一个文件拆成多个独立字节区间并行下载，并用续传账本记录进度。到
0.1.3 为止，账本记录的是**哪些区间已完成**，而不是这些区间来自**哪个版本的对象**。

如果远端对象在下载过程中发生变化——模型被重新上传、release 资产被重建、镜像在后
台把自己补全——变化之后取到的区间来自新对象，却被写在变化之前那些区间的后面。结果
得到一个既不是旧版也不是新版的文件：**拼接体**。下载随后报告成功，完成标记也认同
这个结论。

0.1.3 已经把账本绑定到 URL，所以**不同 URL** 之间不会互相续传。缺口在于**同一个
URL 在不同时刻返回不同的字节**，而对象被替换时看起来正是这个样子。

## 对你已有的文件意味着什么

用受影响版本下载的文件**只有在其远端于下载期间发生过变化时**才可疑。这不是账本能
事后告诉你的：拼接文件的标记在它自己的规则下是自洽的，而 0.1.5 **仍然接受** 0.1.3
写的标记——它没有任何办法知道字节被混过。

所以该问的不是"我当时用的哪个版本"，而是"我能不能证明这个文件的字节"。有两条路。

## 怎么检查

### 一、对照上游校验和（决定性）

如果项目发布了 `SHA256SUMS`（或任何 `sha256sum` 格式的文件）：

```bash
downctl verify ~/models --checksums SHA256SUMS
```

退出码：

| 码 | 含义 |
|---|---|
| `0` | 全部匹配。你的文件是对的——拼接体会让摘要对不上 |
| `1` | 至少一个文件**不匹配**。删掉它重新下载 |
| `2` | 文件在，但无法证明（没有它的校验和，或没有记录过） |

**不匹配就是信号。** 对一个拼接体计算摘要，只有在两段字节本来完全相同（即对象其实
没变）时才会与上游一致。

### 二、重新下载（没有校验和时）

对无法验证的文件，用 0.1.4 或更新版本重取：

```bash
downctl get <目标> --force
```

`--force` 丢弃已有文件与续传状态。在 0.1.4 及之后，结果不可能是拼接体：分片请求以
对象版本为条件，传输中途变化会把旧分片丢掉而不是留下来。

## 修复改了什么

| 版本 | 变化 |
|---|---|
| 0.1.3 | 账本绑定到 URL（不同 URL 无法续传） |
| 0.1.4 | 账本与完成标记携带对象的**版本见证**；范围请求带 `If-Range` 条件；传输中途变化会丢弃旧分片并如实报告。`downctl verify` 可离线证明文件 |
| 0.1.5 | 探测携带任务自身的请求头，让带凭据的目标以与下载相同的权限被度量——这是 0.1.4 的回归，会让私有下载在开始前就失败 |

## 如果你认为自己有拼接文件

1. 按上面的方式跑 `downctl verify`，记下退出码。
2. 报告 `mismatch` 时，文件必须重新下载——损坏不可修复。
3. 报告 `unverifiable` 时，两个方向都没有证据。凡是你依赖的文件，建议直接 `--force`。
4. 如果**用 0.1.4+ 重新下载后仍然 mismatch**，那是新的缺陷，不是这一条——请报告。
